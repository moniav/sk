## Summary

SK 3.0 still asks the model, in prose, to do things Claude Code can now do deterministically: brief the active task, gather git state, load the right context.
Its evals prove that skills fire, not that commands behave.
On existing code it reads file names and patterns, not the code's structure, and it cannot tell when the docs no longer match the code.
And what reviews and retros learn is written down but not fed back to the reviewers.

| Wave | What it fixes | Size | Benefit in one line |
|------|---------------|------|---------------------|
| A | Session start and command start | S | Every session knows the active task, every git command starts with the facts, at no CLAUDE.md cost |
| B | Proof of behaviour | M, costs eval spend | The review and lifecycle guarantees are measured, and model settings are chosen by numbers |
| C | Brownfield accuracy | L | Docs generated for an existing codebase are right for monorepos and stay checked against the code |
| D | Learning loop | S | A mistake found twice becomes a rule the reviewers check, and planning sees past work |
| E | Design notes | S each | Four structural questions get decided on paper before anyone builds them |

## Principles

1. **Deterministic where it can be.** A hook or a preloaded fact beats an instruction the model may skip.
2. **Measure before tuning.** Wave B lands before any `effort` or model change.
3. **Every installed user pays for a hook.** Hooks stay silent when there is nothing to say, never block, and do nothing if they fail.
4. **No new dependencies.** SK stays plain Node 18 and language-agnostic; anything richer (a language server) is used when the user already has it, never shipped.
5. **The October decisions stand** unless a decision below reopens one.

## Wave A: Reliable starts (target 3.1.0)

### A1 Session-start hook that briefs the active task

**Today:** the first rule in `pkg/CLAUDE.md` tells the model to check `docs/tasks/.current` at session start. Whether it does depends on the model, and after `/compact` the instruction is easily lost.

- **Change:** ship `pkg/hooks/hooks.json` with one `SessionStart` hook that runs `pkg/hooks/session-start.mjs` with exec-form `args` and `${CLAUDE_PLUGIN_ROOT}`. When `docs/tasks/.current` exists, the script adds a short briefing as `additionalContext`: task id, title, status, phase, and the next unticked subtask. When it does not, the script prints nothing and exits 0. Any error also exits 0 with no output.
- **Benefit:** every session starts knowing the active work, without the model having to remember to look, and without a line of always-loaded CLAUDE.md. `/sk:resume` is still there for the full briefing.
- **To verify first:** which `SessionStart` matchers exist (`startup`, `resume`, and whether `compact` is one). If `compact` is not, add the same script on `PostCompact`.
- **Files:** `pkg/hooks/hooks.json`, `pkg/hooks/session-start.mjs` (new); `pkg/CLAUDE.md` (decision N3); `scripts/check.mjs`; `CHANGELOG.md`.
- **Done when:** `npm test` runs the script on Node 18 from a bare copy of `pkg/` in three fixtures (no `docs/`, no `.current`, a valid `.current`) and checks: empty output twice, one valid JSON object once, exit 0 every time; `claude plugin validate ./pkg --strict` passes.

### A2 Git state loaded before a command starts

**Today:** `/sk:pr`, `/sk:commit`, `/sk:finish`, `/sk:code-review`, `/sk:review`, `/sk:resume` and `/sk:task-status` begin by running the same git commands one by one: branch, base branch, status, log. `/sk:pr` makes four calls before its real work.

- **Change:** add a short block of shell injection (`` !`git … || true` ``) at the top of each, which runs when the command loads: current branch, base branch, `git status --short`, and `git log {base}..HEAD --oneline` where the command uses it. Keep the existing steps as the fallback, worded "if the block above is empty", because `disableSkillShellExecution` turns injection off and some sessions are not in a git repository.
- **Benefit:** each command starts with the facts already in front of the model: fewer turns and tokens, and no step skipped because the model assumed the branch.
- **Files:** the seven commands above; `scripts/check.mjs` (every injected command ends in `|| true` and is a read-only git or `date` command); `CHANGELOG.md`.
- **Done when:** the check passes, and a manual run of `/sk:pr` and `/sk:review` with `npm run dev` on Linux and on Windows shows the block filled, plus one run outside a git repository that falls back cleanly.

### A3 `/sk:resume` shows open questions and the last evidence

**Today:** it shows the task, phase and uncommitted work, but not the task's open questions or what was last proven.

- **Change:** add the task's unresolved *Open Questions* rows and the newest row of its *Verification* table to the briefing.
- **Benefit:** the person resuming sees what is blocking and what is already proven, so nothing is re-asked or re-tested.
- **Files:** `pkg/.claude/commands/sk/resume.md`.
- **Done when:** a resume on the worked example task (`docs/tasks/examples/`) shows both sections.

### A4 `/sk:help` starts from the project's state

**Today:** `/sk:help` is a static map. A user has to work out whether they are greenfield or brownfield and what exists already.

- **Change:** preload (as in A2) whether `docs/` exists, whether `docs/prd/` has a PRD, and whether a task is active; suggest the next one or two commands with one line of why, then show the map.
- **Benefit:** a new user gets a concrete next step instead of a map to read.
- **Files:** `pkg/.claude/commands/sk/help.md`.
- **Done when:** three scratch projects (empty, scaffolded, with an active task) each get a different first suggestion.

## Wave B: Proof (target 3.1.0)

### B1 Behaviour evals

**Today:** the 11 cases in `dev-docs/evals/` check only that a model-invoked skill fires. `npm test` checks structure and the scaffold, not what a command does. PR #5 shipped with its review changes marked "not verified".

- **Change:** add behaviour cases using the built-in graders (`tool_used`, `file_exists`, `llm`), each on a small fixture repository:
  - `/sk:code-review` on a diff with one planted bug and three planted noise items: the bug is reported, the noise is not, a coverage line is present.
  - `/sk:review` with an active task: the task compliance table appears, and an unmet criterion gives FIX_FIRST.
  - `/sk:pr` with no evidence in the session: the body says "not verified".
  - `/sk:plan` on a task with an open question: it stops to ask instead of planning past it.
  - A report-only command asked to "just fix it": no `Edit` call.
- **Benefit:** the lifecycle's promises (proof, honest coverage, report-only) are measured, so a prompt change that breaks one is caught before release.
- **Files:** `dev-docs/evals/behaviour/*` (new), `scripts/evals.mjs`, `dev-docs/guides/skill-evals.md`.
- **Done when:** a baseline is recorded under `dev-docs/evals/baselines/`, with its cost noted (decision N2).

### B2 `effort` set by measurement

**Today:** decision 7 in October parked `effort` until evals existed. They exist; nothing has been measured.

- **Change:** with B1 in place, try `effort: low` on `task-status`, `resume` and `recap`, and `effort: high` on `debugger`, `architecture-reviewer` and `plan-reviewer`. Keep each setting only where the evals hold or improve.
- **Benefit:** quick lookups get faster and cheaper; the judgement-heavy agents get more thinking where it pays.
- **Files:** the six files above, `CHANGELOG.md` with the measured numbers.
- **Done when:** each kept setting has a before and after eval result in the changelog.

### B3 Reviewers without the lifecycle CLAUDE.md

**Today:** `/sk:review` sends SK's 85-line lifecycle `CLAUDE.md` into three or four parallel reviewers, where it does not apply. They read `docs/conventions/` anyway.

- **Change:** test `omitClaudeMd: true` (Claude Code 2.1.271 or later) on `security-reviewer`, `perf-reviewer`, `quality-reviewer` and `spec-reviewer`.
- **Benefit:** a few hundred lines less context per `/sk:review`, and reviewers focused on conventions rather than lifecycle rules.
- **Risk:** project rules a user wrote only in `CLAUDE.md` no longer reach the reviewers. Keep it only if the B1 review cases hold.
- **Files:** the four agents.
- **Done when:** the B1 review cases pass with the flag on.

## Wave C: Brownfield accuracy (target 3.2.0)

### C1 Workspace and monorepo detection

**Today:** `/sk:init-docs` reads one manifest and assumes a `src/**` layout. In a monorepo it documents one package, or a blend of all of them.

- **Change:** detect workspaces first: `workspaces` in `package.json`, `pnpm-workspace.yaml`, Cargo `[workspace]`, `go.work`, Gradle `settings.gradle` includes, and nested `pyproject.toml` files. For each package, record its stack, build and test commands in a per-package section of `docs/system/tech-stack.md` and `project-context.md`; the root keeps the shared picture.
- **Benefit:** the generated docs match how the code is actually organised, so later commands (`/sk:plan`, `/sk:test`) run the right package's commands.
- **Files:** `pkg/.claude/commands/sk/init-docs.md`, `update-docs.md`, the `tech-stack` and `project-context` templates in `pkg/docs/` and `docs/`.
- **Done when:** a scratch monorepo with two packages in different languages gets two package sections with the right commands each.

### C2 Use a language server when the session has one

**Today:** call and ownership maps come from file names and text search, which miss indirect calls and mix up same-named symbols.

- **Change:** when the session has a language-server tool (from a plugin the user installed), `/sk:init-docs` and `/sk:update-docs` use it for definitions and references of the entry points they document. Without one, they keep today's search. SK ships no language server.
- **Benefit:** architecture and flow docs follow the real call paths in projects that have the tooling, with no new dependency for those that do not.
- **To verify first:** the tool name and how a command can tell it is available.
- **Files:** `init-docs.md`, `update-docs.md`.
- **Done when:** on a scratch project with a language server, a documented flow lists a call that text search alone misses.

### C3 Docs-to-code drift check

**Today:** `/sk:docs-audit` flags a doc as stale by date and lifecycle label. A doc updated last week but already wrong passes.

- **Change:** add a drift step that compares claims with code, each a pass or fail with the evidence:
  - endpoints in `docs/system/api-reference.md` against routes in the code;
  - tables in `docs/system/database-schema.md` against migrations or models;
  - build and test commands in `CLAUDE.md` against the project's scripts and CI files;
  - files and folders named in `docs/architecture/` that no longer exist.
  The report gives a drift count per doc. `/sk:routines` can schedule it.
- **Benefit:** the docs stay trustworthy, which is the foundation every other command reads first.
- **Files:** `pkg/.claude/commands/sk/docs-audit.md`, `routines.md`.
- **Done when:** on a scratch project with one renamed route and one dropped table, the audit reports exactly those two.

## Wave D: Learning loop (target 3.2.0)

### D1 Recurring review findings become anti-patterns

**Today:** reviewers read the anti-patterns section of `docs/conventions/code-style.md`, but nothing adds to it. A finding that appears in five reviews is rediscovered five times.

- **Change:** `/sk:retro` reads the saved reports in `docs/reviews/`, groups findings by kind, and for any kind seen in two or more reports proposes an anti-pattern row with a before and after example. Following its existing rule, a mechanical repeat becomes a proposed lint rule or check instead.
- **Benefit:** the project's reviewers get sharper with use, and the rules come from this codebase rather than generic advice.
- **Files:** `pkg/.claude/commands/sk/retro.md`.
- **Done when:** with three fixture reports sharing one finding kind, the retro proposes that one row and no others.

### D2 Planning looks at past tasks

**Today:** `/sk:plan` starts each task without looking at finished tasks, though their task files hold decisions, pitfalls and verification evidence.

- **Change:** before planning, search `docs/tasks/` for finished tasks sharing the new task's key terms and files, and read the top two or three. Plain text search; no index or embeddings.
- **Benefit:** known pitfalls and proven approaches carry over to similar work.
- **Files:** `pkg/.claude/commands/sk/plan.md`.
- **Done when:** planning a task similar to the worked example cites it.

## Considered and declined

| Idea | Why not |
|------|---------|
| Shipping tree-sitter for code analysis | Breaks the no-dependency rule; C2 gets the same benefit where a language server exists. |
| Semantic search over past tasks | Needs embeddings; D2's text search is enough at the size of `docs/tasks/`. |
| Two-way sync with Linear, Jira or GitHub Issues | Declined in October; `docs/tasks/` is the source of truth (decision N5). |
| Clickable prototypes becoming component stubs | The `prototype` skill's rule 5: prototypes are documentation and never touch production code. |
| Detailed per-stack templates in `/sk:kickoff` | Commands stay language and framework agnostic. |
| Scaffold regression tests | Already exist in `npm test`. |
| A full PRD-to-implementation test run | Long, costly and noisy; B1 covers the guarantees at a fraction of the cost. |
| Raising the model tier when a subtask keeps failing review | `escalation-rules` already stops after three failures and hands the call to the user. |
| A main status line, output styles, monitors, workflows, agent teams | A plugin can only set the subagent status line; the rest has no SK need, and agent teams are experimental. |
| Hooks that block commits or demand verification | They run for every user; a wrong block costs more than it saves. |

## Risks

| Risk | Mitigation |
|------|------------|
| The A1 hook slows or breaks session start for every user | Exits 0 on any error, prints nothing without a task, tested on Node 18 from a bare `pkg/` copy; one file read, no git calls. |
| Shell injection behaves differently on Windows | CI already runs Windows; A2's done-when includes a manual Windows run. |
| Users who turn off shell injection lose the git facts | The original steps stay as the fallback. |
| Eval spend grows without a limit | Decision N2 sets the budget; costs go in the changelog. |
| B3 hides a user's own CLAUDE.md rules from reviewers | Kept only if the review evals hold; noted in the release. |
| C2 depends on a tool name not yet confirmed | Verified before building; the fallback is today's behaviour. |

## Sequencing

Wave D (3.2.0)  D1, D2 in any order
